## Executive Summary

The `GET_OPTION_BUFFER_LEN` macro is defined as `(Pkt)->Length - sizeof(EFI_DHCP4_HEADER) - 4`, where `sizeof(EFI_DHCP4_HEADER)` is 236 bytes and the additional 4 bytes account for the DHCP magic cookie (total 240). The DHCP4 receive path at `Dhcp4Io.c:963` only guards `UdpPacket->TotalSize >= sizeof(EFI_DHCP4_HEADER)` (236), not the full 240 bytes the macro requires. A crafted DHCP4 OFFER packet with `TotalSize` in [236, 239] passes the receive guard but causes the macro's unsigned subtraction to wrap to approximately 0xFFFFFFFC. This wrapped value is passed as the `Length` argument to `PxeBcParseDhcp4Options`, whose `while (Offset < Length)` loop iterates far past the allocated packet buffer, reading `Option->OpCode` and `Option->Length` out of bounds from heap memory. If the OOB heap scan encounters a byte matching `DHCP4_TAG_MAXMSG` (0x39), `PxeBcParseDhcp4Options` returns a pointer to that OOB location and `CopyMem(MaxMsgSize->Data, &Value, 2)` at line 1215 writes 2 bytes to an OOB heap address, escalating from OOB read to heap corruption. The written value is the constant `HTONS(PXEBC_DHCP4_PACKET_MAX_SIZE)` (line 1214), not attacker data, and the write location depends on existing heap contents.

This advisory is one of a set reported to VulnCheck on 2026-06-25 for coordinated disclosure to the EDK II maintainers. After several follow-ups over the following months no response was received. 126 days after the initial report, ByteRay is publishing the findings in good faith so that affected integrators can assess and remediate them. All findings were identified against EDK II commit `70741a15d9a714323a5598eac47727e60507e22f` (master, 2026-06-21).

## Technical Details

**Controllability:** `EXTERNAL_UNTRUSTED` — confidence: **high**

**Data Flow**

A remote DHCP4 OFFER packet with attacker-controlled `TotalSize` in [236, 239] arrives at `DhcpInput` (`Dhcp4Io.c:963`). The receive guard checks only `TotalSize >= sizeof(EFI_DHCP4_HEADER)` (236), so the crafted packet passes. `Packet->Length` is set to the attacker-controlled size (236–239) at `Dhcp4Io.c:979`. Because `Packet->Length <= 240`, `DhcpValidateOptions` is skipped (`Dhcp4Io.c:999`), leaving `Para = NULL`. `DHCP_IS_BOOTP(NULL)` returns `TRUE` due to the NULL short-circuit (`Dhcp4Io.h:50`), so the guard `!DHCP_IS_BOOTP(Para)` evaluates to `FALSE` and is bypassed (`Dhcp4Io.c:611`). `DhcpCallUser` dispatches the undersized packet to `PxeBcDhcp4CallBack` (`Dhcp4Io.c:624`). The callback evaluates `GET_OPTION_BUFFER_LEN(Packet)` at `PxeBcDhcp4.h:136`, computing `236 - 236 - 4 = 0xFFFFFFFC` (UINT32 underflow). This wrapped value is passed to `PxeBcParseDhcp4Options` at `PxeBcDhcp4.c:1208`, whose `while(Offset < 0xFFFFFFFC)` loop reads `Option->OpCode` and `Option->Length` out of bounds from heap memory (sinks at lines 54 and 68). If the OOB scan encounters a byte equal to 57 (`DHCP4_TAG_MAXMSG`), `CopyMem(MaxMsgSize->Data, &Value, 2)` at line 1215 writes 2 bytes to an OOB heap address, escalating the read to heap corruption.

**Affected Callers**

- `DhcpHandleSelect`
- `DhcpCallUser`
- `PxeBcCacheDhcp4Offer`
- `PxeBcParseDhcp4Packet`

**Sanitization / Security Controls**

- **Receive guard** (`Dhcp4Io.c:963`, `TotalSize >= 236`): Ineffective — threshold is lower than the macro's 240-byte requirement, leaving a [236, 239] gap.
- **`DhcpValidateOptions`** (`Dhcp4Io.c:999`): Bypassed — gated on `Length > 240`; for `Length` in [236, 239] the condition is `FALSE`, so validation never runs and `Para` stays `NULL`.
- **`DhcpHandleSelect` OFFER validation** (`Dhcp4Io.c:611`): Bypassed — `DHCP_IS_BOOTP(NULL)` returns `TRUE`, so the `!DHCP_IS_BOOTP(Para)` guard evaluates to `FALSE` and execution falls through to `DhcpCallUser`.

**Realism:** **High**

## Reproduction

1. Attacker monitors for the victim's DHCP4 DISCOVER broadcast (UDP 67/68).
2. Attacker crafts a DHCP4 OFFER with `TotalSize` = 236–239 bytes (full `EFI_DHCP4_HEADER`, no options/magic cookie).
3. OFFER passes basic checks (`Dhcp4Io.c:988–993`: `OpCode = BOOTP_REPLY`, matching Xid/ClientHwAddr — all spoofable from the sniffed DISCOVER).
4. Attacker sends the crafted OFFER to the victim.
5. Receive guard passes (236 >= 236), `DhcpValidateOptions` skipped, `Para = NULL`, `DHCP_IS_BOOTP(NULL) = TRUE`, `DhcpCallUser` invokes `PxeBcDhcp4CallBack`.
6. `GET_OPTION_BUFFER_LEN` underflows to 0xFFFFFFFC; `PxeBcParseDhcp4Options` scans past the end of the packet allocation (`Dhcp4Io.c:970`) through OOB heap until it reaches a 0xFF end tag, a byte of 57, or unmapped memory.
7. If the OOB scan hits a heap byte == 57 at an option-header position, `CopyMem` writes the constant 2-byte value `HTONS(PXEBC_DHCP4_PACKET_MAX_SIZE)` to an OOB heap address, corrupting adjacent heap objects; if the scan runs off mapped memory first, the firmware faults.

## Impact

Pre-auth adjacent-network OOB heap read that can run off mapped memory and crash the firmware during PXE boot, plus a 2-byte OOB heap write of a fixed value at a location determined by heap contents, corrupting whatever heap object is there. Nothing read is sent back to the attacker, so there is no information disclosure, and the attacker controls neither the written value nor its exact location.

## Remediation and Mitigation

As of commit `70741a15d9a714323a5598eac47727e60507e22f` this issue is unfixed upstream and no CVE has been assigned. Validate the length against its minimum before the subtraction so it cannot underflow. The specific control that is absent or ineffective is identified in the Sanitization / Security Controls list under Technical Details.
