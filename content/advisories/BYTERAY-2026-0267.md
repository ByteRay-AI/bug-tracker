## Executive Summary

In `CreateEventRing`, two `UsbHcAllocateMem` calls are guarded only by ASSERT (DEBUG-only, no-op in RELEASE) before `ZeroMem` dereferences the result. Line 811 allocates the Event Ring buffer; line 812 asserts; line 814 zeros it. The second allocation at line 830 (ERSTBase) follows the identical pattern: ASSERT-only at 831, then `ZeroMem` at 833.

This advisory is one of a set reported to VulnCheck on 2026-06-25 for coordinated disclosure to the EDK II maintainers. After several follow-ups over the following months no response was received. 126 days after the initial report, ByteRay is publishing the findings in good faith so that affected integrators can assess and remediate them. All findings were identified against EDK II commit `70741a15d9a714323a5598eac47727e60507e22f` (master, 2026-06-21).

## Affected Products and Versions

- Vendor: TianoCore
- Product: EDK II (`MdeModulePkg`)
- Affected commit: `70741a15d9a714323a5598eac47727e60507e22f` (master, 2026-06-21). The code is present on that commit and later revisions that have not changed it.
- **Location:** `MdeModulePkg/Bus/Pci/XhciDxe/XhciSched.c:811`
- **Function:** `CreateEventRing`
- **Category:** `error_handling`

## Technical Details

**Controllability:** `SYSTEM_CONTROLLED` — confidence: **high**. Called during XHCI controller initialization, not directly from external input. Failure requires memory pressure during controller setup.

**Data Flow**

At line 811, `Buf = UsbHcAllocateMem(Xhc->MemPool, Size, TRUE)` returns NULL on failure. At line 812, `ASSERT(Buf != NULL)` is a no-op in RELEASE. At line 814, `ZeroMem(Buf, Size)` dereferences NULL. A second allocation at lines 830–833 follows the identical pattern (ERSTBase).

**Affected Callers**

- `XhcInitSched` (`XhciSched.c:642`), called from `XhcDriverBindingStart` (`Xhci.c:2102`) and `XhcReset` (`Xhci.c:214`)

**Sanitization / Security Controls**

- ASSERT — DEBUG-only.

## Reachability and Preconditions

Attacker position and trust level for this issue are stated in the Controllability line and Data Flow above, and the concrete trigger is in Reproduction below.

**Exploitability:** **Low**  
**Realism:** **Low**

## Reproduction

1. Memory pressure during XHCI controller initialization; RELEASE build.
2. `CreateEventRing` calls `UsbHcAllocateMem` at line 811.
3. `UsbHcAllocateMem` returns NULL under memory pressure.
4. `ASSERT(Buf != NULL)` at line 812 compiles to no-op in RELEASE builds.
5. `ZeroMem(Buf, Size)` at line 814 dereferences NULL, crashing the firmware.

## Impact

Denial of service — firmware crash during XHCI controller setup.

## Remediation and Mitigation

As of commit `70741a15d9a714323a5598eac47727e60507e22f` this issue is unfixed upstream and no CVE has been assigned. Check the allocation result for NULL before dereferencing it and fail the operation cleanly when allocation fails. The specific control that is absent or ineffective is identified in the Sanitization / Security Controls list under Technical Details.
