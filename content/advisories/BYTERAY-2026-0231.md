## Executive Summary

The device-controlled LBA Data Size (`Lbads`) field — a full `UINT8` (0–255) from the NVMe Identify Namespace response — is used directly as the shift amount in `(UINT32)1 << Lbads` without any bounds validation. The only check before the shift is on the metadata size (`Ms != 0`). For `Lbads >= 32` this is an overshift producing undefined behavior. On x86 and AArch64 the hardware masks a register shift count to 5 bits, so the result is still a power of two; `BlockSize == 0` depends on how the compiler and target handle the oversized shift. Values 0 to 31 are also accepted, so the device can already set nonsense block sizes such as 1 or 2^31. The resulting `BlockSize` propagates to `Device->Media.BlockSize` and is used in all subsequent block I/O operations, where a zero value divides by zero and a very large value overflows the byte count. The same pattern is replicated in `NvmExpressMediaSanitize.c:159` (Format NVM path) and `NvmExpressPei.c:140` (PEI phase).

This advisory is one of a set reported to VulnCheck on 2026-06-25 for coordinated disclosure to the EDK II maintainers. After several follow-ups over the following months no response was received. 126 days after the initial report, ByteRay is publishing the findings in good faith so that affected integrators can assess and remediate them. All findings were identified against EDK II commit `70741a15d9a714323a5598eac47727e60507e22f` (master, 2026-06-21).

## Technical Details

**Controllability:** `EXTERNAL_UNTRUSTED` — confidence: **high**

**Data Flow**

The NVMe Identify Namespace command (`NvmeIdentifyNamespace()` at `NvmExpress.c:95`) issues a command to the external NVMe device, which returns device-controlled `NamespaceData`. The `Lbads` field (UINT8, 0–255) is extracted at `NvmExpress.c:158` from `NamespaceData->LbaFormat[LbaFmtIdx].Lbads` with no bounds validation — the only check is `Ms != 0` at line 147. At line 159, the unsanitized `Lbads` is used as a shift amount in `Device->Media.BlockSize = (UINT32)1 << Lbads`, triggering undefined behavior for `Lbads >= 32` (overshift). The unvalidated `BlockSize` propagates downstream to `NvmExpressBlockIo.c:42` (`Bytes = Blocks * BlockSize`, which can overflow for a large `BlockSize`), `NvmExpressBlockIo.c:193` (`MaxTransferBlocks = (...) / BlockSize`, divide-by-zero if `BlockSize == 0`), and `NvmExpressBlockIo.c:203` (`Buffer += MaxTransferBlocks * BlockSize`).

**Affected Callers**

- `EnumerateNvmeDevNamespace`
- `NvmeFormatNvm`
- `NvmeReadSectors`
- `NvmeWriteSectors`
- `NvmeRead`
- `NvmeWrite`

**Sanitization / Security Controls**

- Only `Ms != 0` check at line 147 — does NOT validate `Lbads`. No sanitization points or security controls exist for the shift amount.

## Reachability and Preconditions

Attacker position and trust level for this issue are stated in the Controllability line and Data Flow above, and the concrete trigger is in Reproduction below.

**Exploitability:** **Low**  
**Realism:** **Low**

## Reproduction

1. Craft malicious NVMe device firmware returning Identify Namespace response with `Lbads` set to 32+.
2. Connect device.
3. Boot system triggers enumeration.
4. `Ms==0` passes the only check.
5. `1 << Lbads` produces UB.
6. Invalid `BlockSize` propagates.
7. Block I/O runs with the invalid `BlockSize`; if the shift produced 0, the divide at `NvmExpressBlockIo.c:193` crashes firmware.

## Impact

Mis-sized block I/O or a firmware crash (denial of service during boot) in the DXE or PEI NVMe driver, triggered by a malicious NVMe device with physical PCIe access. Such a device can already reach memory through DMA on systems without an IOMMU.

## Remediation and Mitigation

As of commit `70741a15d9a714323a5598eac47727e60507e22f` this issue is unfixed upstream and no CVE has been assigned. Validate that the shift count is within the range of the operand width before shifting. The specific control that is absent or ineffective is identified in the Sanitization / Security Controls list under Technical Details.
